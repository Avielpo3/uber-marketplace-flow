Technical spec · v6 · ph-uk (EMEA)

Uber Marketplace Flow

The switch is replaced by the existing NewOrderMakeline call, which makes mp-uber subscribe to the order in tracker-service. Nothing polls. An Uber Eats order is always delivered by us, either by a store driver or, when none is free in time, by a daas-uber courier. Uber Eats only receives order statuses and courier locations. mp-uber sends both the same way for every order and never knows which kind of carrier delivered it.

revised 2026-10-22SPEC.md (full written spec)repos: algo · daas-uber · daas-gateway · tracker-service · mp-uberfile:line refs checked against local checkouts
Switch replaced

/order/switch is replaced by the existing NewOrderMakeline status call, which registers the order in mp-uber and creates its tracker subscription. Nothing calls switch-fulfillment-type any more, so the order stays a restaurant delivery (BYOC).

mp-uber doesn't know the carrier

Statuses come from Algo and from tracker order events. Locations arrive through the existing tracker subscription push, under the same Redis key for store drivers and DaaS couriers.

2 blockers, 1 question with Sergey

tracker-service isn't deployed and EMEA has no Redis (DevOps). Sergey has the question of which Uber Direct status means started.

03Step by step

1

Algo registers the order and reports statuses NewOrderMakeline replaces switch existing call

Algo → daas-gateway → mp-uber · POST /mp/uber/order/status → Uber Eats
Decision
checkForMPOrder algo AggregatorsAPI.go:3139. If a store driver is free within MarketPlace.carrierThreshold (30 min), the store carrier is used, as today. If not, the order goes to daas-uber (step 2).
One call
Decided: the switch, the create delivery and NewOrderMakeline are merged into one request, NewOrderMakeline, sent in both branches. mp-uber already handles it: it inserts its marketplaceorderstatus row as received and subscribes to the order in tracker-service (SubscribeToLocationsOnStatus = NewOrderMakeline) uberMpEventsService.go:42, :99-116. Nothing is sent to Uber Eats.
Statuses
NewOrderMakeline when the carrier is chosen, EnRoute at pickup, Delivered at the end. The calls are identical for both carriers. mp-uber maps them through TriggerUpdatesOrderStatuses (default EnRoute,Delivered) mp-uber configuration.yaml:22.
To Uber Eats
POST /eats/orders/{aggOrderId}/restaurantdelivery/status. started for EnRoute and earlier, delivered for Delivered. Deduplicated for 30 min uberMpEventsService.go:317-339.
DaaS orders
Algo's order reaches EnRoute and Delivered from the daas-uber callbacks. AutoEnrouteOnAggPickup moves it to EnRoute on pickup AggregatorsEvents.go:614. Verify that Algo sends these MP status calls on any carrier's transition, not only for store drivers.
Retries
updateMarketPlaceWithDecision: 6 attempts, backoff 1–16 s :3289.
2

Algo books daas-uber only changed

Algo → daas-gateway → daas-uber · POST /api/v2/deliveries → POST /api/v1/deliveries/
When
Only in the "no store driver in time" branch of checkForMPOrder :3198, which today calls the switch. The switch call there is replaced by the step 1 NewOrderMakeline.
Why it's work
Algo does not pick the provider. In multi-DaaS, ParseAggRequest blanks AggProvider :693, and the provider comes from the gateway quote :847-866.
Mechanism
New dispatchMPOrderToDaas does three things. It sends NewOrderMakeline to mp-uber (step 1). It runs ParseAggRequest and sets AggProvider="uber" and Marketplace=MapOfAggMPSources[source] FrontEndService.go:335. It skips SendQuote and calls SendDelivery, then sendDeliverySetCarrier.
Gateway
Decided: the gateway honours aggProvider. When it is set, /api/v2/deliveries forwards straight to that provider with no quote fan-out. Check daas-gateway router.go:92-103 and change it there if it doesn't already.
On failure
Fall back to the store carrier. mp-uber already has its row and doesn't notice the difference.

4

daas-uber forwards every marketplace callback Algo callbacks as today + one POST per callback

Where
Uber() internal/server/providers.go:52-145, after the existing gateway callback :136.
Condition
marketplace != "". Every Uber Direct webhook for the delivery is forwarded, both courier_status and delivery_status. That covers every status from pending to delivered, plus canceled and returned, with or without a location. Normal DaaS deliveries are untouched.
Market
daas-uber puts market (e.g. ph-uk) in the body. It resolves it from brand+country in its config and falls back to a new default, AGG_DEFAULTMARKET (ph-uk in EMEA). tracker-service also falls back to its DEFAULT_MARKET if market is empty.
Send
A goroutine POSTs to {CallbackURL}/marketplace/uber/callbacks after the Algo callback: up to 3 attempts (backoff 1 s, 2 s), 3 s timeout each. Statuses like delivered come only once, so a lost one is not replaced by the next webhook. A failure is logged and doesn't affect the Algo callback.
Fix
Copy location whenever lat/lng exist, not only when a courier name or vehicle is set providers/uber/delivery.go:372-381.

6

tracker-service stores callbacks and points new consumer

Consumer
New amqp091-go consumer on marketplace_callbacks: prefetch 50, manual ack, nack without requeue on bad JSON (to the DLQ), reconnect loop.
Callbacks
Every message is saved as an order event in a new list tr-svc:market:{m}:store:{s}:posorder:{o}:mpcallbacks with a 24 h TTL, so the order's full Uber Direct history is kept. The key name is proposed.
Forwarding
The consumer adds each new point and order event to the order's forwarding source (tr-svc:fwd:…) types/consts.go:34-36. The existing forwarding job runs every interval, picks them up and POSTs them to the subscribers, here mp-uber. This is a separate path from POST /events/location, which is the mobile-app flow from the Proxy.
Same key
When the message has a location, the point is also written with the existing list write ordersRepository.go:404-431 to tr-svc:market:{m}:store:{s}:posorder:{o}:locations. That is the key store-driver points from the Proxy (POST /events/location) already use, so readers see one list per order whatever the carrier.
TTL
24 h, refreshed on every write. That is already the orderLocations setting configuration.yaml:55-58.
Limit
Decided: raise REDIS_MAX_LOCATIONS_PER_ORDER from 100 to 360, about 2 h at one point every 20 s configuration.yaml:53.

tracker-service forwarding job → daas-gateway → mp-uber · POST /mp/uber/order/events → Uber Eats
Mechanism
The existing tracker v2 subscription. mp-uber creates it on NewOrderMakeline with callback {gateway}/mp/uber/order/events and events location and order trackerV2Service.go:30-80. It works the same for store drivers and DaaS couriers, and there is no push-to-pull cutover.
Handler
The existing ProcessOrderEventsBatch uberMpEventsService.go:120-170 handles order events first, then sends the newest point with processLocationEvents once the order is started :162-164.
Order events
Decided: the Uber Direct statuses are pushed too. processOrderEvents :253-292 turns them into started / delivered for Uber Eats. Algo's EnRoute / Delivered still arrive through /order/status. The 30 min dedup key per order and status stops a double call to Uber Eats types/consts.go:15-20.
Store id

Interval
The tracker forwarding job's existing interval tracker-service configuration/startup.go:115-120.

07Failure handling

What failsEffectHandling
NewOrderMakeline (1)mp-uber has no row and no subscription, so no location reaches Uber Eats6 retries through updateMarketPlaceWithDecision. mp-uber also inserts the row and subscribes if the first call it sees is EnRoute.
daas-uber booking (2)No courierStore carrier delivers. Uber Eats sees no difference, because nothing was promised.
Marketplace callback POST (4)A callback is missing from tracker's history. Algo still gets it.3 attempts, then logged. A lost location is replaced by the next webhook in about 20 s.
Queue or tracker down (5, 6)Points waitThe queue is durable and messages expire after 15 min. The gateway buffers 2000 in memory server.go:98.
Forwarding push or Uber Eats (7)Position lagsThe forwarding job's existing retry and source TTL (15 min) apply. mp-uber sends only the newest point.

08Rollout and tests

Order of release

  • DevOps (separate ticket): provision Redis and the queue in EMEA, and deploy tracker-service with the consumer.
  • Deploy daas-gateway with the new callbacks route. Keep the switch route until algo is released.
  • Deploy daas-uber with the migration. It only acts when marketplace is set.
  • Deploy mp-uber with the order-event mapping. The subscription is unchanged.
  • Deploy algo with the switch replaced by NewOrderMakeline. Pilot one store through Aggregators/MPSources.
  • Remove the old switch route and code.

End-to-end check (staging)

  • A store-driver order behaves exactly as today.
  • A DaaS order: NewOrderMakeline creates the tracker subscription, and points from the queue are pushed to /mp/uber/order/events.
  • A DaaS order: the algo_discovery row has marketplace='uber'.
  • Each webhook, including delivered, gives one Algo callback and one marketplace callback POST, both 202.
  • The Redis key grows and its TTL is about 86400.
  • Uber Eats gets started, then locations, then delivered, each status once.
  • A normal daas-uber delivery sends no marketplace callback.

asked Sergey

Which Uber Direct status means started?

Order events are now pushed, so mp-uber can send started before Algo reaches EnRoute (Algo only does at dropoff). Options: pickup (courier assigned), pickup_complete, or dropoff.

out of scope

Uber Direct cancels or returns

The order is already registered with mp-uber when Uber Direct reports canceled or returned. Undecided: hand it back to a store driver (points then come from the Proxy on the same key), rebook daas-uber, or report a failure to Uber Eats.

out of scope

Uber Direct webhook signature

daas-uber never calls Uber.AuthWebhook providers/uber/auth.go:17, so webhooks are not verified. It stays that way in this change.

decided

Statuses pushed too

tracker-service pushes the Uber Direct statuses to mp-uber as order events. Algo's statuses still arrive, and the 30 min dedup prevents double calls to Uber Eats.

decided

daas-uber only

Algo sets aggProvider=uber and skips the quote. The gateway honours aggProvider and forwards to daas-uber only.
