Technical spec · v4 · ph-uk (EMEA)

Uber Marketplace Flow

The switch is replaced by a regular create-delivery call to mp-uber, which tells mp-uber which orders to pull locations for. An Uber Eats order is always delivered by us, either by a store driver or, when none is free in time, by a daas-uber courier. Uber Eats only receives order statuses and courier locations. mp-uber sends both the same way for every order and never knows which kind of carrier delivered it.

revised 2026-10-22repos: algo · daas-uber · daas-gateway · tracker-service · mp-uberfile:line refs checked against local checkouts
Switch replaced

/order/switch becomes /mp/uber/order/delivery, which registers the order in mp-uber. Nothing calls switch-fulfillment-type any more, so the order stays a restaurant delivery (BYOC).

mp-uber doesn't know the carrier

Statuses come from Algo. Locations come from tracker-service, under the same Redis key for store drivers and DaaS couriers.

2 blockers, 4 decisions

tracker-service isn't deployed and EMEA has no Redis. Decisions cover market lookup, point limit, auth, and the push-to-pull cutover.

03Step by step

1

Algo registers the order and reports statuses create delivery replaces switch status call as today

Algo → daas-gateway → mp-uber · POST /mp/uber/order/delivery, then POST /mp/uber/order/status → Uber Eats
Decision
checkForMPOrder algo AggregatorsAPI.go:3139. If a store driver is free within MarketPlace.carrierThreshold (30 min), the store carrier is used, as today. If not, the order goes to daas-uber (step 2).
Create delivery
Replaces the switch. In both branches Algo sends POST /mp/uber/order/delivery with the regular create-delivery body (the same AggRequest it sends to DaaS). mp-uber upserts its marketplaceorderstatus row with pullLocations = true. That row is the list the poller in step 7 reads. Nothing is sent to Uber Eats.
Statuses
NewOrderMakeline when the carrier is chosen (mp-uber inserts its row), EnRoute at pickup, Delivered at the end. The calls are identical for both carriers. mp-uber maps them through TriggerUpdatesOrderStatuses (default EnRoute,Delivered) mp-uber configuration.yaml:22.
To Uber Eats
POST /eats/orders/{aggOrderId}/restaurantdelivery/status. started for EnRoute and earlier, delivered for Delivered. Deduplicated for 30 min uberMpEventsService.go:317-339.
DaaS orders
Algo's order reaches EnRoute and Delivered from the daas-uber callbacks. AutoEnrouteOnAggPickup moves it to EnRoute on pickup AggregatorsEvents.go:614. Verify that Algo sends these MP status calls on any carrier's transition, not only for store drivers.
Retries
updateMarketPlaceWithDecision: 6 attempts, backoff 1–16 s :3289.
2

Algo books daas-uber only changed

Algo → daas-gateway → daas-uber · POST /api/v2/deliveries → POST /api/v1/deliveries/
When
Only in the "no store driver in time" branch of checkForMPOrder :3198, which today calls the switch. The switch call there becomes the step 1 create delivery.
Why it's work
Algo does not pick the provider. In multi-DaaS, ParseAggRequest blanks AggProvider :693, and the provider comes from the gateway quote :847-866.
Mechanism
New dispatchMPOrderToDaas does three things. It sends the step 1 calls to mp-uber. It runs ParseAggRequest and sets AggProvider="uber" and Marketplace=MapOfAggMPSources[source] FrontEndService.go:335. It skips SendQuote and calls SendDelivery, then sendDeliverySetCarrier.
Gateway
With aggProvider set, /api/v2/deliveries must forward to that provider only. Verify daas-gateway router.go:92-103.
On failure
Fall back to the store carrier. mp-uber already has its row and doesn't notice the difference.

07Failure handling

What failsEffectHandling
Create delivery (1)mp-uber never pulls this order's locations6 retries through updateMarketPlaceWithDecision. Statuses still reach Uber Eats.
NewOrderMakeline (1)mp-uber has no row, so no status or location reaches Uber Eats6 retries. mp-uber also inserts the row if the first call it sees is EnRoute.
daas-uber booking (2)No courierStore carrier delivers. Uber Eats sees no difference, because nothing was promised.
Location POST (4)One point lostLogged. The next webhook arrives in about 20 s.
Queue or tracker down (5, 6)Points waitThe queue is durable and messages expire after 15 min. The gateway buffers 2000 in memory server.go:98.
Poller or Uber Eats (7)Position lagsThe next tick retries from lastLocationTs. Only the newest point is sent.

08Rollout and tests

Order of release

  • Provision Redis and the queue in EMEA. Deploy tracker-service with the consumer.
  • Deploy daas-gateway with the new location route and /mp/{provider}/order/delivery. Keep the switch route until algo is released.
  • Deploy daas-uber with the migration. It only acts when marketplace is set.
  • Deploy the mp-uber poller and run it alongside the push subscription with sending off. Compare points, then switch.
  • Deploy algo with the switch replaced by create delivery. Pilot one store through Aggregators/MPSources.
  • Remove the old switch route and code, and the push subscription.

End-to-end check (staging)

  • A store-driver order: status and location reach Uber Eats from the poller.
  • A DaaS order: the algo_discovery row has marketplace='uber'.
  • Each webhook gives one Algo callback and one location POST, both 202.
  • The Redis key grows and its TTL is about 86400.
  • started on pickup, then locations, then delivered.
  • A normal daas-uber delivery sends no location POST.

09Open decisions

decide

Market in tracker

The Redis key needs a market (ph-uk), but the message has brand and country. Recommendation: map brand+country to market in tracker config, with DEFAULT_MARKET as the fallback.

decide

"All" locations

The list is capped at 100 points today. Recommendation: 360 points (2 h at 20 s), with TTL 24 h.

decide

Auth on the new route

Callbacks and /mp/* have no auth, and the JWT Authenticator is never mounted daas-gateway api/middleware/authenticator.go:14. Recommendation: match callbacks for the pilot, then add service JWT.

decide

Pull for every order

Moving store-driver orders from push to pull touches live UK traffic. Recommendation: run both side by side for a week (step 4 of the rollout) before removing push.
